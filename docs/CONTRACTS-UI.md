# قراردادهای بین‌بخشی — یادداشت اتصال (امیرعلی)

این یادداشت دقیقاً همان چیزهایی است که برای «وصل شدن» سه فاز UI به مسیر واقعی بازی لازم است. هر بخش یک طرف قرارداد را نشان می‌دهد؛ اگر سمت سرور/موتور آماده نیست، سمت UI بی‌صدا خاموش می‌ماند و هیچ خطای کنسولی تولید نمی‌کند.

---

## ۱. حضور هم‌تیمی‌ها — فاز ۱۲ + قرارداد #104

### ارسال (کلاینت → سرور)

```
POST /api/rooms/{roomCode}/presence
x-seat-token: <توکن صندلی>
content-type: application/json

{ "position": { "x": 0, "y": 1.65, "z": -3 }, "yaw": 1.5708, "phase": "alley_puzzle" }
```

- **`playerId` و `seatIndex` در بدنه نیستند**؛ هویت از توکن خوانده می‌شود. این جلوی جعل هویت را می‌گیرد.
- **`yaw` رادیان است** و در بازهٔ `[-π, π)` نرمال می‌شود؛ `yaw = 0` یعنی نگاه به `-z`.
- نرخ ارسال: حداکثر ۱۰ هرتز (`PRESENCE_SEND_INTERVAL_MS = 100`)، فقط وقتی موقعیت بیش از ۵ سانتی‌متر یا چرخش بیش از ۱ درجه تغییر کند، به‌علاوهٔ یک `keepalive` هر ثانیه.
- بدنهٔ ناقص یا مقدار غیرمتناهی (`NaN`/`Infinity`) اصلاً ارسال نمی‌شود (`buildPresencePublishBody` → `null`).

### دریافت (سرور → کلاینت، روی استریم موجود)

```
GET /api/rooms/{roomCode}/stream?token=<توکن>
event: presence_update
data: { "presences": [ ... ], "serverNow": 1792610264622 }
```

هر عنصر `presences`:

| فیلد | نوع | الزامی | توضیح |
|---|---|---|---|
| `playerId` | string | ✅ | شناسهٔ یکتا |
| `position` | `{x,y,z}` | ✅ | فاصلهٔ متری؛ `y` ارتفاع چشم ≈ ۱٫۶۵ |
| `yaw` | number | ✅ | رادیان |
| `pitchDeg` | number | ➖ | درجه؛ فقط برای عنوان/کجی، اختیاری |
| `playerName` | string | ➖ | نام نمایشی |
| `seatIndex` | number | ➖ | برای برچسب «هم‌تیمی صندلی ۳» |
| `phase` | string | ➖ | فاز بازی |
| `lastUpdate` / `receivedAt` | number | ➖ | میلی‌ثانیه؛ اگر نباشد `receivedAt` و سپس `lastUpdate` استفاده می‌شود |

پاک‌سازی: بازیکنی که ۳۰ ثانیه به‌روزرسانی نداشته باشد از HUD حذف می‌شود (`PRESENCE_OFFLINE_TIMEOUT_MS`). سقف نمایش ۳۲ نشانگر است.

### fail-safe سرویس غایب

`usePresenceFeed` پیش از هر اتصال دائمی، یک `GET` کوچک با مهلت ۳ ثانیه انجام می‌دهد:

- **۴۰۴/۴۰۵/پاسخ نامعتبر** → `available = false` و hook **برای همیشه ساکت** می‌شود (نه polling، نه EventSource دوم، نه ۴۰۴ پشت‌سرهم).
- **پنج خطای پیاپی ارسال** → ارسال متوقف می‌شود؛ خواندن ادامه دارد.

یعنی امروز که `presence/route.ts` وجود ندارد، بازی دست‌نخورده کار می‌کند. روزی که سرور اضافه شد، بدون تغییر کلاینت روشن می‌شود.

## ۲. سیگنال ترس — فاز ۰۷-ب (تصمیم #91)

```
<HorrorSignalHud level={'calm' | 'tense' | 'panic'} />
```

| سطح | برچسب | نبض | ویگنت | لرزش | ضربان |
|---|---|---|---|---|---|
| `calm` | آرام | ۰٫۰۸ | ۰٫۱۶ | ۰ | ۱۴۰۰ms |
| `tense` | دلواپس | ۰٫۵ | ۰٫۳۴ | ۱px | ۹۰۰ms |
| `panic` | وحشت | ۰٫۸۵ | ۰٫۵۵ | ۲px | ۵۶۰ms |

- هر مقدار ناشناخته/`null`/عددی → `calm`. کامپوننت هرگز با دادهٔ خراب به حالت وحشت گیر نمی‌کند.
- **وابستگی صفر به `src/engine3d/**`.** موتور (علیرضا) فقط عدد/رشته می‌دهد.
- اعلان `role="status"` فقط هنگام **تغییر** سطح خوانده می‌شود، نه در هر رندر.
- `prefers-reduced-motion` → همهٔ انیمیشن‌ها خاموش، ولی لبهٔ قرمز و متن باقی می‌ماند.

**نقطهٔ اتصال آینده:** اگر snapshot یک `fearLevel` بین ۰ و ۱ آورد، `horrorLevelFromFear(fear)` آن را با آستانه‌های ۰٫۳۲ و ۰٫۶۴ به سه سطح تبدیل می‌کند.

## ۳. جلسهٔ پنل ادمین — فاز ۰۹-ب

```
GET /api/admin/session
→ 200 { ok: true, user: { … } }   // جلسه معتبر
→ 401 / 403                        // بدون جلسه → /admin/login?next=…
→ 404 / 500 / خطای شبکه            // وضعیت نامعلوم → هیچ کاری نمی‌کنیم
```

- فقط `401` و `403` باعث ریدایرکت می‌شوند. `404` یعنی سرویس هنوز نیست؛ ریدایرکت کردن آن‌گاه پنل را در حلقهٔ بی‌پایان می‌انداخت.
- مسیر `next` فقط وقتی ساخته می‌شود که مقصد یک مسیر داخلی `/admin/**` باشد؛ `https://…` و `//host/…` دور ریخته می‌شوند (open redirect).
- صفحهٔ `/admin/login` خودش هرگز ریدایرکت نمی‌شود.
- هیچ توکنی در `localStorage`/`document.cookie` نوشته نمی‌شود؛ کوکی `httpOnly` مال سمت سرور است.
- نام مسیر در ثابت `ADMIN_SESSION_ENDPOINT` (فایل `src/app/admin/login/login-rules.ts`) متمرکز است. اگر امیر نام دیگری انتخاب کرد، **فقط همین یک خط** عوض می‌شود.
