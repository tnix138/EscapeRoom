### نکته‌های الزامی

| موضوع | قاعده |
|---|---|
| `yaw` | **رادیان** و در بازهٔ `[-π, π)` نرمال می‌شود — نه درجه |
| هویت | `playerId` و `seatIndex` از **توکن صندلی** خوانده می‌شود؛ اگر بفرستی نادیده گرفته می‌شود |
| `phase` | همان `GamePhase`: `alley_puzzle` \| `door_cutscene` \| `theater_cutscene` \| `in_theater` |
| `lastUpdate` | اختیاری و ساعت کلاینت؛ سرور `receivedAt` خودش را مرجع انقضا می‌داند |
| نرخ | ۵ تا ۱۰ بار در ثانیه از کلاینت |
| سقف سرور | ۵۰ درخواست در ثانیه برای هر صندلی → بیشتر: `429 RATE_LIMITED` |
| محدودهٔ کوچه | `x ∈ [-9, 9]` · `y ∈ [0, 3.2]` · `z ∈ [-18, 8]` |
| محدودهٔ سالن | `x ∈ [-14, 14]` · `y ∈ [0, 7]` · `z ∈ [-22, 14]` |
| خارج از محدوده | `400 VALIDATION_ERROR` با پیام فارسی «موقعیت خارج از محدودهٔ جهان است…» |
| توکن نامعتبر | `401 INVALID_SEAT_TOKEN` |
| اتاق ناموجود | `404 ROOM_NOT_FOUND` |
| بدنهٔ خالی/خراب | `400 VALIDATION_ERROR` با پیام فارسی |

### نمونهٔ ارسال در کلاینت (علیرضا — فاز ۰۴)

```ts
const PRESENCE_PERIOD_MS = 100; // 10Hz — سقف سرور ۵۰/ثانیه است، پس حاشیهٔ امن داریم

export function createPresenceSender(roomCode: string, seatToken: string) {
  let lastSentAt = 0;
  let inFlight = false;

  return function sendPresence(
    state: { position: { x: number; y: number; z: number }; yawRad: number; phase: string },
    now = performance.now(),
  ): void {
    if (inFlight || now - lastSentAt < PRESENCE_PERIOD_MS) return;
    lastSentAt = now;
    inFlight = true;

    void fetch(`/api/rooms/${roomCode}/presence`, {
      method: 'POST',
      headers: { 'content-type': 'application/json', 'x-seat-token': seatToken },
      body: JSON.stringify({
        position: state.position,
        yaw: state.yawRad, // رادیان
        phase: state.phase,
      }),
      keepalive: true,
    }).finally(() => {
      inFlight = false;
    });
  };
}
```

> تبدیل درجه به رادیان: `rad = deg * Math.PI / 180`. `PlayerTransform` فعلی در `src/engine3d/types.ts` از `yawDeg` استفاده می‌کند؛ تبدیل را در لایهٔ حضور انجام بده و `types.ts` را تغییر نده.
> مثال بالا ارسال‌های موازی را هم مسدود می‌کند (`inFlight`) تا در شبکهٔ کند، صف درخواست نسازیم.

## ۲) دیدن هم‌تیمی‌ها

روی همان استریم موجود مشترک شو:

```http
GET /api/rooms/{CODE}/stream?token=<seatToken>
```

```text
event: presence_update
data: {
  "presences": [
    {
      "playerId": "seat-2",
      "seatIndex": 1,
      "playerName": "علیرضا ب",
      "position": { "x": -3, "y": 1.65, "z": 2 },
      "yaw": 1.2,
      "phase": "alley_puzzle",
      "lastUpdate": 1792610264571,
      "receivedAt": 1792610264571
    }
  ],
  "serverNow": 1792610264622
}
```

- رویداد اول بلافاصله بعد از اتصال می‌آید (`presences` ممکن است خالی باشد).
- سرور رویدادها را با **هم‌جوشی ۵۰ms** می‌فرستد؛ تأخیر دیدن حرکت < ۲۰۰ms است.
- فقط **آخرین** snapshot هر بازیکن نگه داشته می‌شود؛ تاریخچه‌ای نیست.
- بازیکنی که ۳۰ ثانیه چیزی نفرستد از `presences` حذف می‌شود؛ کلاینت هم باید خودش بازیکن را پاک کند.
- `receivedAt` ساعت **سرور** است؛ برای هم‌زمانی از `serverNow` استفاده کن، نه ساعت مرورگر.
- در پیلود، بازیکن **خودت** هم هست (با `seatIndex` خودت)؛ در رندر آن را حذف کن.

## ۳) ⚠️ محدودیت‌های شناخته‌شده (مهم برای کلاینت)

1. **حافظه‌ای است، نه ماندگار.** snapshotها در حافظهٔ پروسهٔ سرور نگه داشته می‌شوند. با ری‌استارت سرور یا سرد شدن نمونه، همه پاک می‌شوند. کلاینت باید این حالت را عادی بداند: اگر `presences` خالی آمد، وضعیت قبلی را پاک کند و از نو بسازد.
2. **در محیط چند-نمونه‌ای یکسان رفتار نمی‌کند.** `presence_update` از طریق hub حافظه‌ای (`src/server/realtime/room-hub.ts`) پخش می‌شود؛ این فقط وقتی درست کار می‌کند که یک نمونه همهٔ اتصال‌های یک اتاق را داشته باشد. برای انتشار روی Vercel چند-نمونه‌ای، این موضوع در #88 به‌عنوان ریسک ثبت شده و راه‌حلش (Supabase Realtime یا polling) هنوز تصمیم‌گیری نشده است.
3. **در فاز ۰۳ روی room state ذخیره نمی‌شود** — پس `ClientRoomView` تغییری نمی‌کند و نسخهٔ اتاق بالا نمی‌رود؛ حضور کاملاً از کانال `presence_update` می‌آید.
